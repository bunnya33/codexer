使用仓库中的 `npm run server:deploy -- ...`。当前目录不是 Codexer 仓库时，读取本技能目录下安装器生成的 `workspace.json`，在其中的 `repository` 目录执行。先读仓库 `AGENTS.md` 和 `docs/server-deploy.md`；发布版本时同时参考 `docs/release.md`、`docs/server-update.md` 及发布工作流。

## 区分交付目标

- “发个服务器更新”“发布更新包”：按既有正式发布流程生成 Release，不据此安装生产服务器。
- “更新到服务器”“帮我安装服务器更新”：授权对已配置服务器执行部署，包含更新器准备、重启和核验。已有这一明确授权时直接执行，无须重复询问；不擅自更新 Agent、Android 或其它服务器。
- 创建工具、登录、查看状态、预检不意味着现在就要部署。

## 登录与预检

运行 `npm run server:deploy -- status`，确认实际服务器地址、当前版本、平台、上传能力和任务状态。仅使用本工具自己的加密会话，不读取浏览器登录存储、Agent 普通账号凭据或向输出打印会话文件。

未登录或会话过期时，运行 `npm run server:deploy -- login --url <已确认服务器根地址>`，将返回的本机登录页交给用户完成管理员登录。既有服务器明确使用 HTTP 时加 `--allow-http`。不要让用户把密码发到对话；不改变服务器会话期限，也不添加后台保活。用户登录后继续原任务。

## 发布并部署

遵守仓库主目录 main 的开发约定，保留无关改动。需要新版本时先完成测试、版本递增和正式发布，等待发布工作流成功，核对固定仓库的目标 tag、源码提交、正式包和同名 SHA-256；不要将仅完成本地构建描述成已发布。

优先从本机下载固定仓库 `bunnya33/codexer` 的正式包和校验文件，再由本工具上传，避免依赖生产服务器拉取 GitHub。按 `status` 的平台选择 `codexer-server-X.Y.Z-linux-amd64.tar.gz` 或对应 arm64 资产。

先运行：

```text
npm run server:deploy -- deploy --archive <正式包的绝对路径>
```

核对返回的地址、from/to 版本、平台和摘要。用户已要求安装到该服务器时执行相同命令加 `--apply`，持续查看进度直到退出，不将“已上传”“built”或短暂断线当作成功。工具会记录任务 ID、等待准备完成、只提交一次重启、检查最终任务、当前版本、health 及管理员接口。

出现 `failed`、`rolled-back`、任务被替换、401 或超时就报告具体阶段及任务 ID；不要盲目重复上传/重启。用 `status` 检查实际结果。本地回执与远端任务一致时，重新执行能接续原任务；已发出但结果不明的重启不会自动重发。保留服务器更新器原有回退机制，不通过此工具执行 SSH、任意命令或 root helper 更新。

最终给出服务器地址、原/新版本、任务结果和核验结果；未安装或未完成时明确说明，不显示凭据。源码、文档、Skill 模板进入仓库，账号和任务回执留在本机配置目录。
