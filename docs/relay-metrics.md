# Relay 性能指标

登录管理员后，仪表盘顶部的「服务器资源」面板展示整机 CPU、内存及 Codexer 进程 CPU、驻留内存、Go 堆和协程数，以及系统分区与数据目录所在分区的空间；同一分区合并显示。默认每 30 秒刷新，可切换为 1 分钟，也可手动刷新。切到后台或离开仪表盘暂停请求，返回时立即读取；失败保留上次数据并明确提示，不把旧数据当成刷新成功。只查看当前快照，不保存历史曲线。

资源面板使用 `GET /v1/admin/system/resources`，仅管理员可读，响应 `Cache-Control: no-store`。服务器按需采集并在所有管理员间共享 15 秒缓存，首次 CPU 采样时缩短为 1 秒；面板在约 2 秒后自动取得第二个样本。没有常驻采样任务，不扫描目录、不统计文件体积、不调用外部监控服务，只读取系统计数器、进程信息和两个目标分区的容量。手动刷新也尊重采样缓存，界面显示实际采样时间。运行环境不支持或无法读取的指标返回 null，界面显示「—」。

CPU 使用两次累计计数的差值计算，两项 CPU 均以整机总算力为 100%，多核服务器不会显示成数百个百分点；整机把 idle 与 I/O wait 计作空闲，Linux guest 时间不重复计算。页面显示实际采样窗口，超过 90 秒未采集则重新建立短时基线，避免展示长时间平均值。内存已用定义为总量减可用量，可回收缓存计入可用；进程内存使用 RSS/Windows working set，不用 Go 堆代替进程占用。磁盘不显示 Codexer 文件体积，只显示相关分区的总量、已用、可用及文件系统；受权限/挂载影响时可局部缺失。容器部署只能读取当前运行环境可见的资源，数值可能来自宿主机或命名空间，不代表 cgroup CPU/内存限额。外部 PostgreSQL、反向代理和更新构建进程不计入 Codexer 进程占用，但会影响整机指标。

需要更详细诊断时，使用同一 bearer session 请求 `GET /v1/admin/metrics`。普通账号返回 403，未登录返回 401。响应不缓存，不含账号、设备 ID、消息、凭据和 SQL。此接口用于单实例诊断，尚未提供 Prometheus 格式。

## 字段与窗口

| 字段 | 内容 |
| --- | --- |
| `process` | 进程运行秒数、RSS/heap/external/arrayBuffers 字节数、累计用户/系统 CPU 微秒 |
| `process.eventLoop` | 保留旧响应字段，Go 返回 monitoring:false 和零值；新增 process.goroutines |
| `scheduler` | 当前设备队列数，以及 device/exclusive/maintenance 三类任务的 waiting/running/completed/failed |
| `queues` | 各类任务的排队与执行耗时分布 |
| `database` | 查询耗时、查询错误、事务耗时与回滚次数；事务耗时包含连接/数据库等待，不等于纯 SQL 执行耗时 |
| `http` | 完成请求的耗时分布和 5xx 次数；包含登录和指标请求 |
| `events` | 事件持久化耗时及失败次数；不包含排队，排队单独看 queues |
| `connections` | 在线设备/已认证客户端、订阅设备/订阅数、待历史/图片/文件回包数（`pendingFiles`）、当前 WebSocket 总缓冲及最大单连接缓冲字节数 |
| `transport` | 广播耗时、累计成功接收连接数、发送消息/字节数，以及背压/超大消息关闭次数 |
| `cleanup` | 清理耗时、累计删除行数、失败/达到预算次数，以及最近一轮各目标的删除行数、批次数、预算/取消状态 |

计数和耗时分布从当前进程启动后累计，重启会清零；数据库统计包含启动迁移。`count` 是样本数，`meanMs`/`maxMs` 是平均/最大耗时，P50/P95/P99 根据固定毫秒桶计算，为桶上界近似值。`buckets` 是每个桶的独立样本数，`upperMs:null` 表示超过 5000 毫秒，使用观察到的最大值估算该桶百分位。指标保存固定数量桶，不保存每次请求记录或按设备分组数据。

CPU 是累计消耗量，比较两次快照的差值判断最近消耗，不能把累计微秒直接当 CPU 使用率。Go 没有 Node 事件循环采样；该字段不应作为 Go 性能判断依据。所有延迟由单调时钟测量，不受登录超时测试或系统墙上时钟调整影响。

## 排查顺序

1. `scheduler.lanes.device.waiting` 与 `queues.device.wait` 同时上升：设备任务处理跟不上输入，查看事件和数据库耗时。
2. `scheduler.lanes.exclusive` 堆积：登录或身份变更屏障在等待已有设备任务。当前登录密码校验仍在屏障内，不属于独立并行登录实现。
3. 数据库耗时高：关注连接池、SQL/锁等待和数据库资源。SQLite 的单连接限制与外部 PostgreSQL 不同。
4. CPU 和广播耗时同时升高：关注消息大小、JSON 处理与订阅数量。
5. 单连接缓冲量与 `backpressureCloses` 上升：客户端消费或网络较慢。关闭只作用于该连接。
6. `cleanup.cappedRuns` 持续增长：本轮预算不足以追上过期数据增长，结合最近一轮删除量和数据库负载调整内部批量/轮次设置。

## 清理与并发保证

每批最多 500 行，每类清理目标每轮最多 20 批，通常每 5 分钟执行；达到预算后默认 5 秒续跑，清完后恢复正常间隔。轮次之间不重叠。删除条件在 DELETE 外层再次检查，避免到期会话被并发续期后仍按旧条件删除。每批单独提交，后续失败不会回滚已完成批次；关闭信号在下一批之前生效，并停止安排后续轮次。命令幂等记录和 pending 微信通知不被定期清理。

不同设备可并行，同设备事件、命令和同步保持顺序；命令超时状态写入排在此前已登记的 Agent 回包之后。账号/会话变更建立全局屏障：先完成此前登记的设备任务，再撤销身份，后续任务重新验证权限。维护清理不占用这个屏障。在线连接仍保存在单进程内，本次优化不提供跨实例连接路由。
